# Point Niebloid Purification

Import: [3D Renderer](index.md)

## Scope

- Reduce `sak::point` (`include/sak/geometry/point.hpp`) to pure coordinate storage and range compatibility, so the class carries no algorithm.
- Move the operations currently declared as members into standalone niebloids under `sak`.
- This is stage 1 of the roadmap and the first executable task of the domain.

## Facts

### Current Member Surface

| Member | Body | Nature |
|---|---|---|
| `is_all( other, operation )` | `all_of( zip( *this, other ), tupled( operation ) )` | generic per-dimension predicate fold |
| `operator==( other )` | `is_all( other, equal_to )` | binding of `is_all` |
| `is_inside( other )` | `is_all( other, less_equal )` | binding of `is_all` |
| `length( )` | `::sak::math::length( *this )` | pure forwarding, no local logic |
| `product( )` | `fold_left( *this, 1, multiplies )` | reduction |

- Evidence: `include/sak/geometry/point.hpp`, the declarations closing the class; `include/sak/math/math.hpp` for `fold_left`, `plus`, `multiplies` and the `lazy_transform`/`zip` primitives reused by the class.

### Already External

- Arithmetic is not implemented by `point`. `operator+`, `operator-`, `operator*`, `operator/`, `operator%` and their compound forms are imported from `::sak::math`, which re-exports the element-wise operators defined over ranges in `include/sak/ranges/operators.hpp`.
- Those operators are generated by the `__781083963_binary` macro, which builds `zip_transform( operation, all( left ), all( right ) ) | to` per overload, with a scalar right operand broadcast through `repeat`.
- Consequence: the class already depends on external niebloids for everything except the four query members and the equality operator. The extraction continues a direction the file already follows; it does not introduce a new one.
- Evidence: `include/sak/ranges/operators.hpp` macro block; the `__using( ::sak::math::, operator+ ... )` import list in `point.hpp`.

### Naming

- The members are named `length` and `product`, without the `get_` prefix, which matches the accessor rule of `docs/agent/style-guide/cpp.md`.
- `docs/agent/sak/cpp/geometry.md` still documents `get_length( )` and `get_product( )` and attributes the operators to a `__352612026_operator` macro that does not exist in the current header. This drift is recorded for later handling and is not changed in this stage.

## Target Shape

- Extract, in this order, one subject per commit-sized change:
  - `product` as a range reduction niebloid, following the `__sak_sum`/`__sak_dot` shape in `include/sak/math/math.hpp` (plain function object, not pipeable).
  - `is_all` as a binary niebloid taking the operation.
  - `is_inside` and the equality predicate as thin named bindings of `is_all` with `less_equal` and `equal_to`.
  - `length` disappears from the class; the existing `sak::math::length` already is the niebloid.
- `operator==` stays declared on the class because value semantics require it, and its body delegates to the extracted predicate. No other operator is declared on the class.
- Every extracted operation consumes the value as a range and never indexes dimensions.
- Placement follows the naming rule that the type carries the concept: a predicate over coordinates belongs to `sak::geometry`, a reduction over a range belongs to `sak::math`. The final split is decided while implementing, since a wrong split is cheap to correct and a premature one is not.

## Exclusions

- No niebloid exists yet for these four operations; this document records the target, not an implementation.
- Nothing in this stage changes the storage, the constructors, or the range compatibility of `point`.
- The stage does not compile and does not run; it produces no measurements.

## Open Questions

- Whether `is_inside` keeps its name or is expressed as `is_inside_of`, given that the extracted form has no receiver to read as the subject.
- Whether the equality niebloid is exposed publicly or stays private to the class, since a public `equal` niebloid would compete with `std::equal_to` in pipelines.

## Relations

- Needs nothing from earlier stages; it is the entry point of the roadmap.
- [Agnostic Pipeline](agnostic-pipeline.md) writes multidimensional formulas as strings, and those formulas are only writable symmetrically if the `sak` primitives they mirror are already niebloids, which is why this stage comes first.
