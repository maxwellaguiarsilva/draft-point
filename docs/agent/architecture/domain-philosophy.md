# Domain Philosophy

This document outlines the core philosophy, priorities, and domain-specific rules for the `draft-point` project.

---

## Priorities

In this project, the functionality of the feature is not the most important aspect, as it is a didactic exploration. The list of priorities must strictly follow the list below in order:

1.  **DRY (Don't Repeat Yourself):** Eliminate redundancy at all costs.
2.  **DDD (Domain-Driven Design):** Reduce visual noise and hide the "machinery" (pointers, manual loops) to let the "data" speak. Code should be a statement of intent ("what"), not a CPU instruction manual ("how").
3.  **SRP (Single Responsibility Principle):** There is no plan to produce code using SRP as a primary goal, as this is a natural consequence if DRY and DDD are effectively met. If SRP fails, it's because DRY and DDD also failed.
4.  **Style and formatting:** Strict adherence to the C++ style guide.
5.  **Feature delivery:** Lastly, and least importantly, the actual delivery of the feature.

## Counterintuitive Code and MCP Tools

To assist in development, there are MCP tools available (provided by `project-mcp-tools`, a sibling repository). 

- **Generated Code:** The code generated by these tools (e.g., class and test scaffolding) **must not be altered**, even if it seems counterintuitive.
- **Trust the Notes:** In this project, there is a lot of counterintuitive information and code. Relying on these notes and models saves tokens in the context of the LLM and time, which will not be wasted on repeatedly checking subjects already tested in the past. A good example is the formatting patterns inherent to language models mentioned in the style guides.

## Exceptions to the Language Rule

While all code and documentation must be in English (US), there is one specific exception:
- Markdown documents written in Brazilian Portuguese (pt-br) are allowed **only** if they are located within a `docs/analyses/pt-br/` folder.
